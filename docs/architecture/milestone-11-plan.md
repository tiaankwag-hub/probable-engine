# Milestone 11 Implementation Plan — CODE AND TERRAFORM COMPLETE, NOT YET APPLIED

GCP deployment hardening: real production identity (retiring the mock-auth backdoor),
Terraform for the full stack the roadmap already promised, and the exact runbook to apply it.
Consistent with every earlier milestone plan's own constraint, **no GCP resource was created
from this development environment** — `terraform apply` is Phase 6 of
`docs/architecture/gcp-deployment-runbook.md`, run by the user from their own workstation.

## What was built

### Real identity, retiring the mock-login backdoor (ADR 0010)
`POST /api/v1/auth/mock-login` — a deliberate local-dev-only backdoor that mints a valid token
for any seeded email, no password, no verification — is not merely discouraged in production,
it is **absent from the route table entirely** when `AUTH_MODE=iap` (`apps/api/app/main.py`
only registers `auth.mock_login_router` in mock mode). In its place:
- **`apps/api/app/iap_auth.py`**: verifies Google IAP's signed assertion against Google's
  public keys via `google-auth`, extracting the `email` claim. Never trusts a client-supplied
  role or user ID — only the verified email, looked up in `users` exactly like every other
  identity path.
- **`apps/api/app/deps.py`**: `get_current_user` now dispatches on `Settings.auth_mode`. The
  `iap` path accepts the assertion from either `X-Goog-IAP-JWT-Assertion` (what IAP itself
  injects for browser traffic) or a forwarded `Authorization: Bearer <google-id-token>` (what
  the MCP gateway presents, since it never goes through IAP at all) — both are verified
  identically, because both really are just Google-signed JWTs for one audience.
- **`GET /api/v1/auth/me`** (added, but useful independent of this milestone) is what lets any
  client holding nothing but a token confirm its own identity — the MCP gateway's
  `TokenVerifier` already depended on this from Milestone 10.

### Internal-only endpoints for Cloud Scheduler
**`apps/api/app/routers/internal_jobs.py`**: two routes (`/internal/jobs/ingest-emerging-signals`,
`/internal/jobs/capture-snapshot`) with **no app-level auth check at all** — deliberately, not
an oversight (see the router's own docstring). Their safety is entirely the surrounding
platform: `apps/api`'s Cloud Run ingress is never public, and the service additionally requires
IAM authentication, so a request only reaches this code after Cloud Run's platform has already
verified an OIDC token from an identity holding `run.invoker` on this specific service —
exactly what Cloud Scheduler is configured to present (`infra/modules/scheduler_job`).

### `apps/worker` gets a health-check server, nothing else
Cloud Run requires every service to bind a port and answer health checks; `apps/worker` was a
pure polling loop with no server at all. Added a minimal `ThreadingHTTPServer` on `$PORT`
answering 200 to anything, running in a background thread alongside the unchanged polling loop
(`apps/worker/app/main.py`). The actual job-processing logic — what gets polled, how jobs are
claimed, `SELECT ... FOR UPDATE SKIP LOCKED` — is untouched.

### apps/mcp's dual-identity headers
Milestone 10's gateway forwarded exactly one token in one header. Production changes what that
header needs to prove: `apps/api`'s Cloud Run ingress now requires an IAM-authorized caller
before any request reaches app code at all — a platform-level check entirely separate from "is
this a valid human identity", which is what the app code itself still verifies. `RiskPlatformClient`
and `RiskPlatformTokenVerifier` (`apps/mcp/app/api_client.py`, `apps/mcp/app/auth.py`) now send
**two** headers on every call to apps/api: `Authorization` carries the gateway's own service
identity (minted via `google-auth`'s `fetch_id_token` against the Cloud Run metadata server,
falling back to the caller's own token when that metadata server doesn't exist — i.e. every
environment except real Cloud Run, where this whole mechanism is simply inert and harmless),
and `X-Goog-IAP-JWT-Assertion` always carries the caller's own token as-is, which is what
`apps/api`'s app-level identity check actually reads. Same code, two environments — the
gateway never checks which mode it's running in.

### Terraform (`infra/modules`, `infra/environments/production`)
See `infra/modules/README.md` for the full module list and what's deliberately not built
(Cloud Tasks queue, VPC, monitoring dashboards). The production environment composes them into:
Artifact Registry; a private (no public IP) Cloud SQL instance whose password and full DSN are
generated by Terraform and stored directly into Secret Manager, never passed through a
variable; a private Storage bucket; five least-privilege service accounts (one per deployable
service, plus one for Cloud Scheduler); four Cloud Run v2 services; a single external HTTPS
load balancer with Google IAP enabled on **two** backend services (web at the default path,
api at `/api/*`) so `apps/web`'s existing `NEXT_PUBLIC_API_BASE_URL`-based browser client keeps
working completely unmodified; and two Cloud Scheduler jobs.

`api` and `worker` share one ingress setting, `INGRESS_TRAFFIC_INTERNAL_LOAD_BALANCER` — a
superset that permits both the load balancer's routed traffic and same-project internal
callers (mcp's direct calls to api, Cloud Scheduler), never the public internet hitting either
service's raw `*.run.app` URL directly. `mcp` stays fully internal — reached only via
`gcloud run services proxy` (see the runbook) or a deliberately-granted individual
`run.invoker` binding, never a public endpoint of its own.

### The deployment runbook (`docs/architecture/gcp-deployment-runbook.md`)
Eleven ordered phases, from project creation through DNS and verification, each naming exactly
what to replace. The two genuine bootstrapping subtleties it calls out explicitly: Cloud Run
needs a real, already-pushed image at creation time, so Artifact Registry is created via a
deliberately targeted `terraform apply -target=module.artifact_registry` before any image
exists (Phase 4) and before the full apply (Phase 6); and Cloud SQL has no public IP at all, so
migrations run as a one-off Cloud Run Job reusing the `api` image (Phase 8), the same pattern
`docker-compose.yml`'s `migrate` service already uses locally.

## Verified

- Full existing test suite (462 tests, `apps/api`/`apps/worker`/`packages`) still green after
  every change in this milestone.
- New tests: IAP assertion verification (valid/expired/wrong-claim/unreachable), auth-mode
  route registration (mock-login present only in mock mode, `/me` working identically via
  either header in iap mode, a mock-style token correctly failing real verification), the
  internal-jobs router reachable with zero auth headers in either auth mode, and apps/mcp's
  dual-header behavior on and off simulated Cloud Run — 19 apps/mcp tests, 462 apps/api tests.
- Live, in this environment: restarted apps/worker directly and confirmed its health endpoint
  answers 200 while the poll loop keeps running unmodified; re-ran the full Milestone 10 MCP
  client round-trip (list tools, real data, RBAC denial passthrough) after every auth-related
  change in this milestone to confirm nothing regressed.
- **Not verified live**: the Terraform itself. No `terraform validate`/`plan`/`apply` was run —
  no Terraform binary is available in this development environment, and even if there were,
  applying real GCP infrastructure from here would violate the same boundary this whole
  milestone exists to enforce. The runbook's Phase 4/6 `terraform validate` step is the first
  real check this configuration gets, and is called out as exactly that: not a formality.

## Explicitly still deferred

- **Cloud-Tasks-native worker** — `apps/worker` runs as a fixed single always-on Cloud Run
  instance polling Postgres exactly like local dev, not migrated to the Cloud-Tasks-push model
  ADR 0005 originally described (and which was never actually built in any environment before
  this milestone either — the `JobQueue` interface ADR 0005 describes doesn't exist yet; every
  router inserts directly into `background_jobs`). A real push-based worker needs: a
  `JobQueue` abstraction actually introduced in `packages/shared`, an HTTP push-receiver
  endpoint in `apps/worker` (Cloud Tasks calls it, rather than the worker polling), and five
  routers (`ai.py`, `reports.py`, `imports.py`, `emerging_risks.py`, `simulations.py`) switched
  from a raw `BackgroundJob` insert to that interface. Worthwhile once autoscaling worker
  capacity actually matters; not before.
- **A user-management admin UI** — provisioning real users (Phase 10 of the runbook) is a
  manual `psql` step today. IAP controls who can sign in; this app's own `users`/`user_roles`
  tables still gate what they can do, and there's no UI yet for populating the latter.
- **CI/CD pipeline and scanning gates** — the roadmap's own Milestone 11 line item, left to the
  user's own CI system rather than built here; Artifact Registry's built-in vulnerability
  scanning is already active at no extra Terraform once its API is enabled.
- **Vertex AI provider swap** — `packages/ai`'s `GeminiProvider` still calls the public
  Gemini API directly via `GEMINI_API_KEY`; `VertexGeminiProvider` (documented since Milestone
  8 as a one-file future addition implementing the same `AIProvider` protocol) is not built.
  Not required for this migration — Secret-Manager-backed `GEMINI_API_KEY` works identically in
  production — only relevant if the organization's compliance posture specifically requires
  routing model calls through Vertex AI rather than the public API.
- **Staging/dev GCP environments** — only `production` was built; see the two environments'
  own READMEs for how to extend using the same modules.
